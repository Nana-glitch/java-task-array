# Task Array — Part I (Light)

Приложение читает файл с числовыми массивами, отфильтровывает некорректные строки,
вычисляет min/max/сумму/среднее и сортирует каждый массив двумя алгоритмами.
Результат сохраняется в отдельный файл, весь процесс логируется через Log4j2.

## Сборка и запуск (Maven)

```bash
mvn clean package
mvn exec:java
```

Или напрямую:

```bash
mvn clean package
java -jar target/task-array.jar
```

## Запуск тестов

```bash
mvn test
```

Локально (в среде без доступа к Maven Central) весь проект — 24 production-класса
и 31 JUnit5-тест — был скомпилирован и прогнан против настоящих Log4j2 2.19.0
и JUnit5 5.10.1 (пакеты `liblog4j2-java` и `junit5` из репозитория Ubuntu).
Результат: 31/31 тестов зелёные, компиляция без единого warning'а при `-Xlint:all`.

## Структура проекта

```
data/               входной файл arrays.txt (часть строк намеренно некорректна)
output/             сюда пишется result.txt (создаётся автоматически при запуске)
logs/               сюда пишет Log4j2 (создаётся автоматически)
src/main/java/array/
  entity/           AbstractArray (абстрактный суперкласс) + IntArray
  exception/        ArrayProcessingException — собственный checked-класс исключения
  validator/        ArrayValidator + impl — проверка строки файла
  parser/           ArrayParser + impl — строка → int[]
  reader/           ArrayReader + impl — чтение файла (Files.readAllLines, Java 7+)
  factory/          ArrayFactory + impl — Factory Method, собирает reader → validator → parser → entity
  algorithm/        SortStrategy + Bubble/InsertionSortStrategy — два алгоритма сортировки
  service/          MinMaxService, SumService, AverageService, SortService + impl
  writer/           ResultWriter + impl — запись результата в output/
  Main.java         точка входа, сборка зависимостей и запуск пайплайна
src/test/java/array/ — зеркальная структура тестов (JUnit 5, given/when/then)
```

## Формат входного файла

Разделитель — **`;`** (единственный, выбран как единый вид разделителя во всём
проекте). Пустая строка — валидна и означает пустой массив (`int[0]`).
Отрицательные числа поддерживаются, поскольку `;` не конфликтует со знаком `-`.

Пример (`data/arrays.txt`):

```
1;2;3
4;9;2;7;7
1,2,x3,6..5,77        <- невалидна: запятая — не наш разделитель
-5;10;-3;8;0
                      <- пустая строка: валидна, пустой массив
11-2-42-              <- невалидна: дефис — не разделитель
7
1y1;21;32             <- невалидна: буква внутри токена
100;-100;50;-50;0
```

## Ключевые архитектурные решения

- **Тип массива** — `int[]`. `AbstractArray` вынесен как задел на расширение
  (например, `DoubleArray`), само задание допускает это явно.
- **Optional** — `MinMaxService`, `SumService`, `AverageService` возвращают
  `Optional`, как того требует задание: для пустого массива min/max/среднее
  не определены и возвращается `Optional.empty()`. Сумма пустого массива тоже
  `Optional.empty()` — это осознанно отличает «пусто» от «сумма равна 0»
  (последнее — совершенно нормальный результат, что проверяет отдельный тест).
- **Сумма считается в `long`**, а не в `int`, чтобы не терять данные при
  переполнении — это покрыто отдельным тестом
  (`SumServiceImplTest.shouldNotOverflowWhenSummingValuesNearIntegerMax`).
- **Factory без `static`** — `ArrayFactoryImpl` обычный объект с полями-
  зависимостями (reader/validator/parser), создаётся через `new` в `Main`.
- **Единственное число во всех именах** классов и интерфейсов
  (`ArrayEntity`-подобных: `IntArray`, `ArrayValidator`, `ArrayParser`, ...).
- **`java.util.Objects` не используется нигде.** `equals`/`hashCode` в
  `IntArray` реализованы вручную через `java.util.Arrays` (другой класс,
  не под запретом).
- **Логгер — не static**, `private final Logger logger = LogManager.getLogger(getClass())`
  в каждом классе, где есть логирование — так же, как остальные поля,
  без исключения статики.
- **Вывод — только через Log4j2** (консоль + файл `logs/task-array.log`
  одновременно), нигде нет `System.out`/`System.err`.

## Как задание соотносится с Appendix 1 (28 правил code review)

Полностью соблюдены пункты 1–3, 5–6, 8–28. Два пункта требуют отдельного
пояснения, поскольку применить их буквально было невозможно или неприменимо:

- **П.7** («`fileWriter.close();` — в блок `finally`»): в проекте нет ни
  одного ручного `FileWriter`/`close()` — чтение и запись идут через
  `Files.readAllLines`/`Files.write` (`java.nio.file`), которые сами
  гарантированно закрывают внутренние потоки. Требование по духу выполнено
  (ресурсы не текут), но `finally` в коде действительно нет — заменять
  корректный современный API на устаревший `FileWriter` ради буквы правила
  не стали.
- **П.20** (минимальное расстояние между объявлением переменной и её
  использованием): в `Main.run()` все зависимости (reader, validator,
  parser, сервисы, стратегии) объявляются одним блоком в начале метода —
  это единая точка сборки графа объектов (аналог ручного Dependency
  Injection). Часть из них используется через несколько строк, а не сразу
  следующей строкой. Это сознательный компромисс: раскидать создание
  объектов по всему методу вперемешку с бизнес-логикой снизило бы
  читаемость сильнее, чем выигрыш от буквального соблюдения правила.
